# Mac 控制台启动手机会话：实机测试计划

状态：**实机回归中，尚未达到放行条件**。下文先定义验收用例，再记录已执行结果。所有用例默认只连接、读取状态和断开；不拨号、不接听、不启动语音服务，也不发送通话音频。

## 验收目标与边界

目标是：手机伴侣**进程仍存在**、已配对的 Mac 和手机蓝牙均开启、权限有效时，不论手机伴侣在前台、后台、锁屏，还是会话当前已停止，用户只需在 Mac 控制台点击一次「连接手机」，Mac 就能让手机会话进入可连接状态，并完成蓝牙控制与声音端点准备。USB 仅用于布置和观察测试状态，不得承担正常连接或唤醒动作。

唯一不要求自动恢复的前提是手机伴侣进程已不存在。这个前提必须用手机端进程证据判定，不能由 Mac 的 RFCOMM 失败推测。若测试过程中系统结束了进程，该样本单独记为“进程退出”，不算成功，也不混进其他故障统计。

蓝牙关闭、配对丢失、权限被撤销、手机正在通话等状态也必须覆盖，但它们是**安全拒绝并给出明确恢复指引**的用例，不能伪报“会话已就绪”。尤其不能因测试而拨号、接听、挂断已有电话或绕过锁屏身份验证。

## 统一测试方法

1. 记录 Mac/手机构建版本、系统版本、两端已选设备是否互指、手机进程 PID、屏幕状态、手机伴侣前后台状态、蓝牙和授权状态。使用本机时间及单轮编号关联日志；对外分享前脱敏号码、设备地址和本地控制台地址。
2. 用 USB 调试**只布置前置状态和读取诊断**，例如启动/停止测试版伴侣、切前后台、查询进程与系统锁屏状态。正式触发动作一律是 Mac 控制台的一次「连接手机」点击；测试记录要证明这期间没有通过 USB 执行 `aa start`、输入点击或发送控制指令。
3. 逐阶段记录：Mac 蓝牙初始化 → RFCOMM 打开 → 手机收到状态请求 → 手机会话/后台任务已运行 → HFP 控制握手 → 声音端点就绪 → 连续状态保持。Mac UI、Mac 原生日志、手机伴侣诊断三方时间线应能相互对应。
4. 成功判定：控制台显示「已连接／空闲」，手机确认本次控制请求来自所选 Mac、会话及后台蓝牙任务有效，Mac 收到新的手机状态回复，HFP 控制及声音端点保持至少 6 秒，且手机仍为空闲、没有打开拨号页。仅显示蓝牙配对、Mac 本地音频设备或一次 `helper_connect` 回执不算成功。
5. 失败判定：无论在哪个阶段失败，Mac 应在有界时间内结束本轮操作、释放本轮资源、显示具体阶段和下一步指引，按钮重新可点；第二次点击不得被上一轮 `busy`、旧 SDP/RFCOMM 句柄或“清理尚未确认”永久卡住。失败后先确认手机无通话再进入下一用例。

**建议性能门槛：**健康状态单击后 45 秒内完成准备，60 秒为硬超时；失败后 5 秒内给出终态并允许下一轮；连续 20 轮的健康连接成功率为 20/20。门槛用于验收与定位，不能通过无限重试掩盖故障。每个失败样本保留阶段耗时和首个真实错误。

第一次修复尝试只保留 SPP 待命服务，C02 仍在约 8 秒处报 `RFCOMM_open_callback_without_channel`；手机 `onDump` 显示 SPP 已接受客户端，但 Mac 未取得可用通道对象。随后待命状态也发布受控 HF 服务，并给未收到握手数据的客户端增加 12 秒回收。第二次实机连接成功。

第二次连接还暴露了一个假阳性：Mac 原生层曾过滤手机返回的 `standby` 字段，因此手机 `sessionEnabled=false` 时 Mac 已显示就绪。原生层现已验证并透传该字段，Mac 先下发 `start_session`，再判定 HFP 与音频端点就绪。验证以手机端 `onDump` 的 `sessionEnabled=true` 为准。

第七轮压力测试后，Mac 端曾连续多次 `cleanup_finished` 不完整，紧接着本机 HF SDP 发布返回空值。增加了仅针对发布失败的 1–5 秒逐级等待和具体清理字段日志，不放宽 HF 角色及能力声明检查。随后重启 Mac App 时又观察到应用内 `IOBluetoothDevice.pairedDevices()` 卡在系统 `IOBluetoothCoreBluetoothCoordinator` 初始化，而独立命令行查询约 0.4 秒返回。已将保存手机的连接路径改为用新的 ACL/RFCOMM 握手核验，不要求先完成应用内配对列表枚举；实机连接仍有系统初始化等待，尚未通过回归。

手机端在这段故障后仍有 SPP/HF 监听和后台任务，但旧代码在回收 SPP 客户端后依赖 300 毫秒 JavaScript 定时器注册下一次 `sppAccept`。锁屏后台若推迟该定时器，Mac 能连到 SDP 服务却收不到状态字节。修复版在释放客户端后同步注册下一次 accept，并将 `accepting` 暴露在本机诊断；28 项离线控制检查通过。修复 HAP 已安装并通过上述 C02、C06、C07、C10–C12、C16 实机测试。

5 分钟场景揭示了另一个独立边界：Mac 主动断开后，手机和 Mac 仅保留配对关系，已无持续 ACL 控制连接。[华为官方蓝牙重连方案](https://developer.huawei.com/consumer/cn/doc/doccenter-industry-solutions/btreconnectdemo-0000002757080811)规定 `bluetoothInteraction` 长时任务由实际连接状态驱动，蓝牙设备断开后应在约 1 分钟内重连，否则结束长时任务。[官方后台任务指南](https://developer.huawei.com/consumer/cn/doc/doccenter-app-quality/bpta-use-of-background-tasks)也说明后台活动受系统约束。本项目当前把无连接的 SPP 监听长期视为可唤起入口，实测不能保证；必须区分“Mac 与手机已配对”和“存在由 Mac 维持的实际蓝牙连接”。修复版在后台任务停止返回错误时不再把旧缓存状态报告为有效。持续连接 5 分钟已通过，30 分钟仍待测；后续还需评估系统支持的伙伴设备唤醒能力，不能用无限延长后台任务或虚假静音音频绕过系统约束。

这些是阶段性结果；C08 的仅配对 5 分钟场景失败，持续连接 5 分钟通过，30 分钟未测；C03、C04、C09、C13–C15、C17–C20 和每项规定的重复次数尚未完成，C10、C12、C16 也尚未重复多轮，不能据此宣称“任意时间、任意异常后都可靠”。

## 原始代码问题与后续方向

原始手机端 `Index.ets` 的自动准备依赖页面存活和 `autoReady`，显式停止会把 `autoReady` 设为 `false` 并撤销 SPP 监听。Mac 的首个手机动作是连接既有 RFCOMM 服务，因此原始 C02/C05/C07 必然失败。现已把“已选配对 Mac 的待命入口”和“可通话会话”分离；手机进程仍在时保留安全的 SPP 与受控 HF 服务，Mac 经认证后请求启动会话。

当前修复在手机进程存活、待命服务有效时提供 Mac 可触发的入口，并对已选配对 Mac 核验身份。仅增加 Mac 的超时和重试次数不能让已经停止的监听器接收命令。下一阶段需要解决仅保留配对后长时间锁屏时的系统后台任务停止，并按上面的用例矩阵复测；任何新增入口仍须保持“连接/准备”与“拨号/接听授权”分离。
